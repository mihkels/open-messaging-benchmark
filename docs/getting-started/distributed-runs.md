# Distributed runs

A single host quickly becomes the bottleneck when benchmarking a cluster. In distributed mode the
coordinator drives two or more worker processes over HTTP, and each worker runs producers or
consumers with its own driver process.

## How work is split

- At least two workers are required.
- The first half of the worker list (rounded down) runs producers and the rest run consumers. With
  `--extra` (`-x`), only about a third of the workers produce, for drivers such as JMS where
  consumers need more capacity.
- Topics are divided across producer workers, and the target rate is divided evenly across the
  producer workers that received topics. With fewer topics than producer workers, some workers stay
  idle.
- Subscriptions are divided across consumer workers.
- The coordinator sends the driver configuration file contents to every worker. Any other file the
  configuration refers to, such as a certificate or a JMS provider jar, must exist on each worker.
- Payloads are generated by the coordinator and sent to the workers, so `payloadFile` only needs to
  exist on the coordinator host.

The coordinator logs the split at startup:

```text
Workers list - producers: [http://w1:8080,http://w2:8080]
Workers list - consumers: http://w3:8080,http://w4:8080
```

## 1. Start the workers

On each worker host, from a distribution directory or the Docker image:

```bash
bin/benchmark-worker --port 8080
```

```bash
docker run -d --name omb-worker -p 8080:8080 openmessaging-benchmark:local \
  bin/benchmark-worker --port 8080
```

Each worker is a small supervisor process. When the coordinator initializes a driver, the worker
starts a separate JVM with that driver's plugin and any required delegate plugins on the classpath,
and stops it when the next driver is initialized. The driver JVM heap defaults to 4 GiB; set
`HEAP_OPTS` on the worker to change it. See [Runtime and plugins](../reference/runtime-and-plugins.md).

> **Note:** `--stats-port` is deprecated and ignored, but it must differ from `--port`. Its default
> is 8081, so pass `--stats-port` with another value if you run the worker on port 8081.

Workers expose Prometheus metrics at `http://<worker>:8080/metrics`; see
[Monitoring](../guides/monitoring.md).

## 2. Run the coordinator

List the workers on the command line:

```bash
bin/benchmark \
  --drivers driver-kafka/kafka-latency.yaml \
  --workers http://w1:8080,http://w2:8080,http://w3:8080,http://w4:8080 \
  workloads/1-topic-16-partitions-1kb.yaml
```

Or in a YAML file passed with `--workers-file`:

```yaml
workers:
  - http://w1:8080
  - http://w2:8080
  - http://w3:8080
  - http://w4:8080
```

```bash
bin/benchmark --drivers driver-kafka/kafka-latency.yaml --workers-file workers.yaml \
  workloads/1-topic-16-partitions-1kb.yaml
```

`--workers` and `--workers-file` cannot be combined. If neither is given and a `workers.yaml` file
exists in the current directory, it is used automatically; otherwise the run is local.

The coordinator itself generates no load, so it can run on a small host, but it must reach every
worker on its HTTP port. Workers must reach the brokers.

## Several drivers and workloads

The coordinator accepts several drivers and several workloads and runs every combination in turn:

```bash
bin/benchmark \
  --drivers driver-kafka/kafka-latency.yaml,driver-pulsar/pulsar.yaml \
  --workers-file workers.yaml \
  workloads/1-topic-16-partitions-1kb.yaml workloads/1-topic-100-partitions-1kb.yaml
```

Each combination writes its own result file named after the workload, driver and time. Do not pass
`-o` with more than one combination: every result is written to the same file and only the last one
remains.

## Sizing and placement

- Run workers on hosts separate from the brokers, so client work does not compete with the system
  under test.
- Use at least as many producer workers as you need to offer the target rate with low publish
  delay; watch publish delay latency and the workers' CPU.
- Keep clocks synchronized (for example with chrony) when producers and consumers run on different
  hosts; end-to-end latency compares their wall clocks.
- Use identical worker hosts and placement for every system you compare. See
  [Fair comparisons](../methodology/fair-comparisons.md).

For Kubernetes deployments, see [Containers and Kubernetes](../guides/containers-and-kubernetes.md).
