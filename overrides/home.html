OpenMessaging Benchmark · maintained fork

Benchmark any messaging system with the same workload

OMB drives a workload you define in YAML through Kafka, Pulsar, RabbitMQ and twelve other systems. Every 10 seconds it records publish and consume rate, backlog, and latency percentiles, then writes the whole run to a JSON result.

What a run records

Rates, backlog and three kinds of latency

The coordinator samples every producer and consumer every 10 seconds and keeps full HdrHistogram percentiles for the measured period. A healthy run shows the offered rate met, a flat backlog and a publish delay close to zero. Reading a result

  • msg/s · MB/s

    Publish and consume rate

    Messages acknowledged by the broker and messages received by consumers.

  • messages

    Backlog

    Sent but not yet received, per subscription. Growth means consumers fall behind.

  • ms · p50 … max

    Publish latency

    From the start of the send call until the broker acknowledges the message.

  • µs · p50 … max

    Publish delay

    How late the load generator sent each message against its schedule.

  • ms · p50 … max

    End-to-end latency

    From the producer timestamp until a consumer receives the message.

How a run works

One coordinator, any number of workers

  1. Describe the system and the load. A driver YAML picks the plugin and broker settings; a workload YAML sets topics, partitions, message size, rate and duration.
  2. The coordinator distributes it. bin/benchmark creates topics, producers and consumers on each worker, or runs them itself in local mode.
  3. Each driver runs isolated. Workers start the selected plugin in a child JVM that holds only that driver's libraries.
  4. Statistics come back every 10 seconds. At the end the coordinator aggregates percentiles and writes a JSON result.

Why this fork

Kept current, tested against real brokers

  • Current Java and clients

    Builds and runs on Java 27 with up-to-date client libraries, while tracking upstream OpenMessaging Benchmark.

  • Drivers as isolated plugins

    Every driver ships as a plugin bundle and runs in its own JVM, so client libraries never collide. Runtime and plugins

  • Regression suite per plugin

    A Docker Compose suite runs every plugin end to end against its broker and writes HTML and JUnit reports. Testing a driver

  • Bring your own driver

    Build a plugin outside this repository against the driver API and drop it on the plugin path. Implementing a driver
